# 설치 복구 상태와 사용자 확인 복구

## 목적과 범위
설치가 recovery-required로 중단되었을 때 사용자가 앱에서 이유와 다음 행동을 확인하고 검증된 복구를 요청할 수 있게 한다. 상태 확인은 자동, 시스템 변경은 명시적 확인 후 수행한다. 공장 초기화, 표식 삭제 우회, 자동 재설치는 하지 않는다. 기존 차량의 성공 여부는 이 구현만으로 보증하지 않는다.

## 현재 구조와 선택
MainActivity/StatusModel은 root 소유 UI 상태를 읽고 SwitchRequest로 앱 전용 폴더에 요청을 쓴다. root uilog.sh가 제한된 요청을 처리한다. 기존 앱 제거는 integrated rollback과 다르므로 재사용하지 않는다.

안내만 추가하는 방식은 사용자 수동 작업이 남고, 무조건 자동 rollback은 동의 없는 시스템 변경과 재부팅 위험이 있다. 기존 요청 채널을 확장하되 전용 검증 복구 runner를 두는 방식을 선택한다.

## 화면: 기존 순정형 디자인 유지
- StockSkin/Widgets, 기존 글꼴·행 높이·구분선·사각 버튼·선택/비활성 스타일을 재사용한다. 신규 색상 체계, 둥근 카드, 새 토글은 만들지 않는다.
- 정보 화면 상단에 기존 그룹 행 형태의 설치 상태 요약을 표시한다. 복구 필요 시 원인 요약과 관리 화면 이동을 제공한다. 색만으로 상태를 구분하지 않는다.
- 관리 화면에 설치 복구 그룹을 추가한다. 상태, 마지막 실패 단계, 복구 가능 여부, 최신 갱신 여부를 표시한다. 버튼은 '이전 상태로 복구', '오류 상세', 기존 '진단 저장' 연결이다.
- 확인 화면도 기존 화면 내 확인 패턴을 사용한다. '설치 전 상태로 되돌립니다. 성공하면 재부팅됩니다. 전원을 끄거나 USB를 분리하지 마세요.'와 실행/취소를 표시한다. 주행 여부를 확인하는 신뢰 가능한 신호가 현재 없으므로 '주차 후 실행'을 명시하며 주행 잠금이 있다고 주장하지 않는다.
- 복구 중에는 중복 복구·제거·설정 변경을 잠근다. 읽기와 진단은 경합 없이 안전하게 가능한 범위에서 유지한다. 앱을 닫아도 복구는 계속된다.
- 원인을 읽을 수 없으면 '원인 기록을 읽을 수 없습니다'로 표시한다. 과거 remount 오류를 EBUSY 등으로 추측하지 않는다. I18n에 한국어/영어를 함께 추가한다.

## 상태 계약
기존 bounded status 파일에 recovery_state, recovery_available, recovery_reason, recovery_stage, recovery_request, recovery_result를 추가한다. 값은 허용 목록/길이 제한으로 파싱하고 shell 코드나 임의 경로를 값으로 받지 않는다. 기존 boot/uptime freshness 규칙을 유지한다.

상태는 none, required, working, restored, unknown으로 정규화한다. 설치기 원본 상태는 별도로 검증하여 매핑한다. 읽기 실패·알 수 없는 값·오래된 수집은 unknown이며 정상으로 표시하지 않는다. 최초 설치 오류와 복구 오류를 별도 보존한다. 전체 원문 로그를 상태에 넣지 않는다.

## 복구 실행과 신뢰 경계
1. 릴리스 빌더가 통합 복구에 필요한 현재 runner/검사기/도구/패키지와 manifest를 하나의 복구 번들로 만든다. root 소유 고정 경로에 검증 후 임시 staging에서 원자적으로 게시한다. 새 설치 트랜잭션을 시작하기 전에 준비하며, 이전 설치가 남긴 recovery-required 상태에서도 별도의 복구 준비 진입점으로 갱신할 수 있어야 한다. 준비 작업 자체는 시스템 패치나 기존 snapshot을 변경하지 않는다.
2. 앱은 기존 순번/boot/만료 검사를 따르는 recovery 요청만 쓴다. 경로·명령·환경변수는 보내지 않는다. root는 고정된 게시 번들만 사용하며 USB의 임의 스크립트를 직접 실행하지 않는다. 해시는 손상 검사이고 서명된 배포 인증의 대체가 아님을 명확히 한다. root 소유권과 쓰기 권한, 경로의 심볼릭 링크/파일 유형을 검증한다.
3. 실행 직전 transaction state, 완전한 prior snapshot, 필요한 파일 해시, 도구와 작업 배타성을 다시 검사한다. 'complete' 표식 존재만으로 실행 가능하다고 판정하지 않는다. 실패하면 시스템 변경 전에 거부하고 이유를 남긴다.
4. installer·앱 제거·복구가 같은 작업 잠금을 공유하게 한다. stale lock은 PID만으로 지우지 않고 현재 작업 식별과 프로세스 생존을 확인한다. 요청은 시작 전에 기록하며 중복 전달 시 같은 결과를 반환한다. 앱/collector 수명에 종속되지 않는 root 작업으로 실행하고 진행 상태를 원자적으로 기록한다.
5. 기존 integrated rollback의 백업/패키지 검증과 previous bootguard 재조정 의미를 유지한다. UI collector를 제공하는 core 패키지가 제거될 수 있으므로 복구 worker와 최종 기록은 해당 패키지 밖에 둔다. 진행 수집이 중단되면 앱은 완료로 오인하지 않고 확인 불가 안내를 한다.
6. 최종 검증과 bootguard 재조정 성공 후에만 복구 완료를 기록하고 reboot suppression을 해제하여 cold reboot한다. 실패 시 재부팅/자동 재시도를 하지 않고 복구 필요와 최초/복구 오류를 보존한다. '이전 상태'는 설치 직전 snapshot이며 반드시 순정이나 모든 기능 활성 상태라는 뜻은 아니다.

## 구버전·앱 실행 불가 대응
현재 차량은 새 복구 runner가 없을 수 있다. 이 경우 앱은 '복구 USB 준비 필요'와 정확한 다음 절차를 표시하고 실행 버튼은 비활성화한다. 새 USB의 명시적 복구 준비/실행 진입점으로 기존 snapshot을 보존하면서 복구 가능하게 한다. 단순 새 설치로 표식을 우회하지 않는다.

설치기 진행 화면과 report.sh 결과 문서에도 복구 필요 여부·실패 단계·복구 실행 또는 준비 절차를 제공한다. 앱이 없거나 실행되지 않더라도 안내가 남아야 한다. USB 저장 실패는 차량 내 결과 기록과 별도 오류로 취급한다.

## 시험과 완료 기준
- JVM: 상태 매핑/unknown/만료, 버튼 잠금, 요청 중복, 한국어·영어 문구.
- shell: 정상 복구, 기존 recovery-required, 불완전 snapshot, 해시 불일치, 링크/권한 오류, runner 미설치, 동시 installer/remove/recovery, 중복·만료 요청, worker 중단, 상태 쓰기 실패, rollback/bootguard 실패.
- 중단 후 재진입에서 기존 snapshot을 덮어쓰지 않으며 자동 반복 복구가 없는지 확인한다. 성공 후 재설치 회귀를 포함한다.
- 앱/collector 소실과 USB 분리/기록 실패 시 완료 오표시가 없고 수동 복구 안내가 남는지 확인한다.
- 기존 화면과 같은 해상도에서 정보/관리/확인/진행/실패/unknown/영어/작은 화면을 캡처하여 잘림·터치 영역·디자인 일관성을 확인한다.
- 전체 회귀, 빌드, 산출물 감사 통과를 코드 완료 기준으로 한다. 실차 remount/복구/재부팅 성공은 별도 검증이며 공개 릴리스·USB 갱신은 이번 설계 승인에 포함하지 않는다.
