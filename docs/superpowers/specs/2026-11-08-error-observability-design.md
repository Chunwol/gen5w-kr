# 전체 오류 처리·진단 보강 설계

상태: 구현 전 사용자 검토 대기. 기준 3dc8a7a 및 기존 로컬 hotspot remount 수정.
목표: 실패한 단계·원래 오류·현재 상태·원복 결과를 같은 시도의 기록으로 연결한다.
로그로 모든 원인을 확정하거나 실차 연결 성공을 보장하는 작업은 아니다.

## 요구와 범위

사용자는 부분적인 로그 보강 때문에 차량 재시도를 반복하는 문제를 줄이길 원한다.
이번 완료 범위는 설치만이 아니라 설치/업데이트/제거/복구/부팅 복구,
무선·AP·ADB·HUD·타이머·블루링크·USB logger·화면 요청·진단 수집이다.
기존 로컬 remount 수정과 USB 보고서 증거를 보존한다.
Git 공개 발행·USB 갱신은 이 설계 구현과 별개이며 명시적으로 결과를 구분한다.

## 현재 소스에서 확인한 누락 후보

후보는 확정 오동작 목록이 아니다. 의도된 fallback/정상 probe는 별도 분류한다.

| 경로 | 관찰 | 보강/검증 목표 |
|---|---|---|
| wireless-enable common/preun | rw/ro 원문 폐기, ro 실패 무시 또는 종료 | 명령·단계·rc·mount 상태 보존; 기존 반환 정책 명시 |
| audio-format common/post/preun | rw 원문 폐기, ro 일반 busy 경고만 있음 | 오류 종류와 실제 상태 구분; unknown을 busy로 단정하지 않음 |
| wireless-bridge common/post/preun | rw/ro 원문 폐기 | 적용 및 원복 단계별 기록 |
| bridge bootguard-recover | remount 실패 요약만 남음 | 복구 진입 이유·복원 대상 검증·실패 단계 기록 |
| usb-wifi common | rw/ro 원문 폐기 | 드라이버/모듈/AP 실패와 mount 실패 분리 |
| local-hotspot finish | 로컬 수정 후에도 원복용 rw 원문 폐기 | 최초 실패와 원복 실패 모두 보존 |
| integrated gate/staging/snapshot/rollback | 다수 return1, 상위 단계만 보일 수 있음 | 최초 실패 불변 기록 및 원복 실패 별도 기록 |
| bridge service AP broker launch | app_process stdout/stderr 폐기 | UID 실행·프로세스 종료·bind·broker 실패 단계 구분 |
| report/NEMESIS entry | 한 EXEC_LOG 덮어쓰기, ISSUE는 설치기 요약만 | 이전 실패 보존, 시도 식별자와 진단 위치 연결 |
| diag/check/uilog deep collect | stderr 폐기, pipeline 뒤쪽 성공이 앞쪽 실패를 가릴 수 있음 | 명령 없음/권한/실패/진짜 빈 결과 구분 |
| Java AP/BT transport | false/null 반환 및 일부 무음 catch | 개인정보 없는 원인 코드와 예외 클래스, owner 세대 연결 |
| HUD/provider/service/UI requests | timeout/미지원/쓰기 실패가 요약 또는 무음 | 분류 가능한 실패 이벤트 및 관찰 시점 기록 |
| USB drive logger | 검증 거부/쓰기 종료는 이유 있음 | 실제 USB detach·FUSE 거부·여유 공간·쓰기·logcat EOF 구분 및 수집 확인 |

## 선택한 방식

개별 echo만 추가하면 같은 누락이 반복된다. 반대로 전역 `set -x`와 원시
logcat 무제한 수집은 인증정보 노출·저장장치 소모를 일으킨다. 기존 수집기를
유지하면서 공통 진단 규약과 경계 실행 도우미를 적용한다.

### 이벤트 규약

- 빌드 revision, boot 식별자/uptime, 시도 ID, 모듈, 단계, 작업, 결과, rc,
  안전한 원인 분류, 대상 검증 상태, 원복 결과를 기록한다.
- command 문자열/인수 전체는 기록하지 않는다. 명령 ID는 코드에 정의한 고정값이다.
- 최초 실패는 원복의 후속 오류로 덮지 않는다. 원복 실패·재시도·경고는 별도 이벤트다.
- 실제 rc와 오류 종류가 없으면 unknown으로 기록한다. timeout/권한/미지원/빈 결과를 구분한다.
- 동작 판단에 필요한 명령 stdout과 진단 stderr를 섞지 않는다.

### 저장과 개인정보

- 기존 패키지 로그 및 REPORT를 활용한다. 공통 도우미가 필요하면 빌드 시
  패키지에 포함하여 다른 모듈의 설치 여부에 의존하지 않도록 한다.
- 반복 이벤트는 상태 변경 시 또는 제한 빈도로만 기록한다. 진단 스트림은
  64KiB 단위, 4세그먼트 등 명시한 상한을 두며 활성 로그 하나가 무한 증가하지 않는다.
  실제 상한과 oldest-first 회전은 구현 계획에서 파일별로 고정한다.
- USB 설치 보고서는 최근 시도8개를 유지하고 current 별칭/보고서는 최신 시도를 가리킨다.
  알 수 없는 기존 파일은 삭제하지 않고, 우리 소유·허용된 파일만 순환한다.
- USB가 쓰기 불가하면 가능한 경우 private 내부 bounded 진단에 남긴다.
  내부 저장소도 쓰기 불가하면 고정 logcat 코드로 알리고, 기록 성공으로 표시하지 않는다.
- SSID/PSK/비밀번호/토큰/MAC/VIN/폰 이름/길안내 목적지/미디어 제목/원시 페이로드는 제외한다.
  Java는 기본적으로 예외 클래스와 고정 원인 코드만 기록한다.
- 명령 오류 원문은 검토한 안전한 로컬 파일시스템/패치 명령에 한해 크기를
  제한하고 비식별화한다. 제외한 내용은 redacted/truncated로 표시한다.
- 자동 업로드·제조사 파일 복사·전체 디스크/프로세스 메모리 덤프는 하지 않는다.

### 오류 처리와 상태 수집

- 관측 보강만으로 fail-closed, 순정 소유권 우선, 백업 검증 및 복구 중단 조건을 풀지 않는다.
- 기존 remount 로컬 수정의 검증된 busy 경고만 별도 정책으로 유지한다.
- 실패 시 해당 경계의 제한된 문맥을 수집한다: system/data/USB mount와 공간,
  쓰기/파일 검증 상태, 관련 서비스 생존/단계, AP/인터페이스/드라이버 관찰,
  provider timeout 여부. USB·system 장애를 같은 원인으로 추정하지 않는다.
- 복구 완료는 바이트 검증·runtime 설정·등록 상태의 해당 조건이 모두 맞아야 한다.
  installed 등록은 적용 성공이나 실제 연결 성공으로 취급하지 않는다.
- 로그 실패가 transport cleanup 자체를 중단시키지 않는다. 진단 실패도 관찰 가능한
  별도 고정 이벤트로 처리하며 stderr 재귀 기록/무한 재시도를 금지한다.

## 구현 순서와 완료 기준

1. 모든 소스의 무음 경로를 조사해 audited / intentional / changed / unresolved
   네 분류와 근거를 남긴다. grep 결과 개수만으로 전수 점검 완료라 하지 않는다.
2. 공통 기록·비식별화·회전·명령 경계 계약을 실패 주입 시험으로 먼저 검증한다.
3. 설치/제거/복구/bootguard 및 모듈 명령 경계에 적용한다.
4. 무선·AP·ADB·HUD·UI·USB logger의 런타임 원인 코드를 적용한다.
5. 실패 보고서와 진단에서 최초 실패→원복→최종 상태가 연결되는지 통합 시험한다.
6. 권한 오류, busy, 명령 없음, rc 비정상, 부분 출력, timeout, stale owner,
   디스크 부족, USB 탈착, 로그 쓰기 실패, 프로세스 종료, 원복 실패를 주입한다.
7. 로그에 민감 문자열을 넣어 누출이 없는지, 과도한 반복에도 상한이 유지되는지 확인한다.
8. 전체 회귀·64 on-unit command 호환·API18 앱/DEX 빌드·산출물 감사를 실행한다.
   exact-stock 및 실차가 수행되지 않으면 미검증으로 명시한다.

## 비목표 및 미확인

- Wi-Fi 드라이버·순정 자격 증명·물리 SPP 해제 API를 이번에 새로 구현하지 않는다.
- 사용자가 말한 연결 실패 팝업은 원문/당시 service log가 없어 원인 미확정이다.
- 보고서에 나타난 2026-11-08 remount 오류는 원문이 폐기되어 실제 errno를 복원할 수 없다.
- 모든 오류를 한 번의 로그로 고친다는 보장은 하지 않는다. 누락·관찰 불가도 결과로 남긴다.

## 검토 게이트

설계 자체에는 미정 placeholder가 없고 기존 dirty remount 수정과 충돌하지 않는다.
사용자가 범위·개인정보·저장 상한·보존 정책을 승인한 뒤 구현 계획을 작성한다.
이 문서 작성만으로 제품 코드 구현·전수 시험·배포가 완료된 것은 아니다.
